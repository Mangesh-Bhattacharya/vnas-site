REST API (v1)

Base: https://<host>/api/v1. JSON bodies; every binary field (enc*, wrapped*, keys, salts) is
standard base64. Authenticated calls send Authorization: Bearer <token>. IDs are 32 lowercase
hex characters, generated by clients so that items can be created offline. Chunk IDs are 64 hex characters.

Errors: {"code": "conflict", "message": "...", "details": {...}} with HTTP status. Notable codes:
unauthorized 401, mfa_required 401, bad_credentials 401, forbidden 403, not_found 404 (also used
for "exists but not yours"), conflict 409 (details.current = server item), exists 409,
locked 423, rate_limited 429, quota_exceeded 507.

Items: files, folders, notes, vault entries, records

Item JSON:

{ "id": "…", "spaceId": "…", "parentId": null, "kind": "note",
  "encMeta": "…", "wrappedItemKey": "…", "keyEpoch": 1, "encPayload": "…",
  "currentVersion": 0, "sizeBytes": 812, "revision": 1042, "deletedAt": null,
  "createdAt": 1760000000, "updatedAt": 1760000000, "updatedBy": "…", "updatedDevice": "…",
  "wrapScheme": "space", "intakeStatus": null, "intakeLinkId": null, "aiIndexable": true }

Allowed kinds per space: drive → folder/file · vault → folder/secret · notes → folder/note · records → folder/record.
encPayload (≤ 1 MiB) carries notes, vault entries and records; files use versions.
wrapScheme is "space" (normal, symmetric under the space key) or "intake" (sealed to an intake link's keypair — see
Intake links below); intakeStatus is null except for intake-created items (pending/accepted/rejected);
aiIndexable gates whether the AI assistant may index the item (also a general per-item opt-out — see docs/AI.md).
GET /spaces/{sid}/items?parent=&kind=&deleted=only|include&all=1&intake=pending|all → {items:[…]}. intake defaults to hiding pending intake submissions; pending shows only those
POST /spaces/{sid}/items {id, parentId?, kind, encMeta, wrappedItemKey, keyEpoch, encPayload?} → 201 item
GET /items/{id} → item (vault reads are audited)
PUT /items/{id} {baseRevision, parentId?, moveToRoot?, encMeta?, wrappedItemKey?, keyEpoch?, encPayload?} → item, or 409 conflict
DELETE /items/{id}?baseRevision=N[&purge=1] trash (recursive) / purge (must already be in trash) → 204
POST /items/{id}/restore → item (restores the subtree trashed with it; re-parents to root if the parent is gone)

Password vault CRUD is this API on a vault space with kind: "secret". Payload (encrypted):
{type: "login", fields: {username: {value, updatedAt}, password: {value, updatedAt, concealed:true}, url, totp, notes}}.
Notes CRUD uses a notes space with kind: "note" and payload {format: "markdown", body}.
Organization directory (Admin, Board of Directors, IT, on-site/off-site technicians, clients) uses a records space
with kind: "record" and encPayload.schema = "vnas.directory.v1"; the fixed field set (name, role, phone numbers,
one address, email, and company size for clients) is a client-side convention only — see packages/core/src/directory.ts
and the Directory page in the web client. No server change: it's ciphertext like every other record.

Intake links

Let an anonymous visitor (no account) deposit a record and/or documents into a drive or records space — e.g. a vendor
collecting a customer's inspection report or incident form — without the server ever seeing plaintext. The submitter's
client seals every item key to the link's own X25519 keypair (crypto_box_seal) instead of the space key, which it never
has. Submissions land as normal items with intakeStatus: "pending" and aiIndexable: false; the owner reviews, decrypts
and promotes them (or just trashes/rejects them like any other item). See docs/SECURITY.md T12 for the threat model,
including the residual risk around a removed member and a static intake keypair, and why rotateSpaceKey also re-keys
every active intake link.

Management (authenticated, space member):
POST /spaces/{sid}/intake-links owner/editor on a drive/records space: {parentId, publicKey, wrappedIntakeKey, keyEpoch, formSchema, expiresAt, maxSubmissions?, maxSubmissionBytes} → {id, token, url}
GET /spaces/{sid}/intake-links → {links:[{id, parentId, createdBy, publicKey, wrappedIntakeKey, keyEpoch, formSchema, maxSubmissions, submissionsCount, maxSubmissionBytes, bytesReceived, expiresAt, revoked, createdAt}]}
POST /intake-links/{lid}/revoke → 204
POST /intake-links/{lid}/rotate-key {publicKey, wrappedIntakeKey, keyEpoch} → 204
POST /items/{id}/promote-intake {baseRevision, wrappedItemKey, keyEpoch, aiIndexable} → item; flips wrapScheme to "space" and intakeStatus to "accepted"

Public (no auth; stricter per-IP and per-link rate limits than share links, since this is a write surface):
GET /intake/{token} → {spaceKind, publicKey, formSchema, maxSubmissionBytes, maxFiles, maxChunkBytes, expiresAt}
POST /intake/{token}/chunks/missing {ids:[…]} → {missing:[…]}
PUT /intake/{token}/chunks/{cid} same shape as the authenticated chunk upload
POST /intake/{token}/submissions {submissionId, record?:{…}} for a records link, or {submissionId, folder:{…}, files:[…]} for a drive link → 201 {submissionId}

Unknown, revoked, expired or exhausted links all collapse to the same 404 intake_gone, matching share links' probing
resistance. secret and folder-as-top-level items are never reachable from this path.
