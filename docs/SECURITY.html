Security design

Security is the product. This document is the reference for what vNAS protects, how, and what it
deliberately does not protect. Report vulnerabilities privately; see §9.

1. Assets and trust boundaries

Asset Where it lives Who can read it
File contents, names, tags, notes, vault entries, records Server: ciphertext. Devices: ciphertext cache plus plaintext in memory while unlocked Only members of the space, on unlocked devices
Password The user's head. Never stored or transmitted Nobody
Account master key (AMK) Server: wrapped by the password-derived key and by the recovery key. Device: memory, optionally the OS keystore The user
Structural metadata: IDs, parent links, sizes, timestamps, member lists, emails Server, plaintext Server operator
Audit log Server (hash-chained, signed) Admins

Trust boundary: the server is assumed honest-but-curious, and possibly compromised. Clients
are trusted only while unlocked, on the user's own device.

2. Cryptography (packages/core/src/crypto.ts)

Purpose Primitive Parameters
Password stretching Argon2id (crypto_pwhash) 128 MiB, 3 passes, 1 lane (client default). The server rejects anything below 64 MiB / 3 passes
Key separation BLAKE2b KDF (crypto_kdf_derive_from_key) Context vnasauth: subkey 1 = auth key, 2 = wrap key
Symmetric encryption XChaCha20-Poly1305 (IETF AEAD) 256-bit keys, random 192-bit nonces (safe to generate at random), versioned envelope 0x01‖nonce‖ct
Sharing X25519 sealed boxes (crypto_box_seal) Space keyring sealed to each member
Integrity of files Ed25519 signatures over manifests Device verifies signer
Chunk IDs Keyed BLAKE2b-256 Keyed with the item key, so the server cannot confirm known files
Server-side auth hash Argon2id (Go x/crypto/argon2) 19 MiB, 1 pass. The input is already a 256-bit key
Server secrets at rest (TOTP seeds) AES-256-GCM Key in server-keys.json (0600)
Audit log SHA-256 chain + Ed25519 Per-row signature

Associated data binds every ciphertext to its role and ID (vnas:item-meta:<id>,
vnas:chunk:<item>:<chunk> …), so a malicious server cannot swap one item's ciphertext for another's.

2.1 Key hierarchy

password ─Argon2id(salt)─► master ─┬─► authKey  ──► server stores Argon2id(authKey)
                                   └─► wrapKey  ──► AEAD(AMK)            = wrapped_amk
recovery key (256-bit, printed) ───┬─► recoveryAuthKey ──► server stores its hash
                                   └─► recoveryWrapKey ──► AEAD(AMK)     = recovery_wrapped_amk
AMK ──► AEAD(X25519 sk ‖ Ed25519 sk)                                     = wrapped_private_keys
X25519 pk ◄── sealed {epoch: spaceKey…}                                  = space_members.wrapped_space_key
spaceKey[epoch] ──► AEAD(itemKey)                                        = items.wrapped_item_key
itemKey ──► AEAD(meta), AEAD(payload), AEAD(chunk), AEAD(manifest)

2.2 Login is zero-knowledge

/prelogin returns the public KDF parameters. Unknown emails get a deterministic fake (HMAC of
the email), so account existence is not revealed. The client derives authKey and sends only that.
The server compares Argon2id(authKey) in constant time. A database leak lets an attacker
brute-force passwords only at the full client Argon2id cost, per user.

Residual risk / upgrade path: an aPAKE (OPAQUE, RFC 9807) would remove even the offline-guess
oracle that the stored hash gives a server attacker. It is planned for phase 3; the KDF/auth split
already isolates it to one module.

2.3 Password change and recovery

Changing the password re-wraps the AMK; no data is re-encrypted, and other sessions are revoked.
Recovery uses the printed 256-bit recovery key and still requires the TOTP code or an MFA
recovery code when MFA is enabled. There is no admin password reset by design: an admin who
could reset passwords could read data.

2.4 Sharing and key substitution

A malicious server could hand a sharer an attacker's public key. Clients show a key fingerprint
(Settings) for out-of-band comparison before sharing sensitive vaults. Planned: key transparency
log / TOFU pinning with change warnings (phase 3).

2.5 Key rotation and revocation

  • Remove a member: the owner's client creates epoch n+1, re-seals the full keyring to the remaining
    members, and re-encrypts space metadata. New content uses the new epoch. Old content stays readable
    by current members. Re-wrapping old item keys is lazy, and full re-encryption is optional for files
    the removed member could have cached.
  • Lost device: Settings → Devices → Revoke kills its sessions instantly. If the device had the
    AMK in its keystore, change the password, which re-wraps the AMK and signs out all devices.
  • Compromised account password: change it. Rotate keys of shared spaces if exposure is suspected.
  • Server keys (server-keys.json): rotation re-seals TOTP secrets. Audit-key rotation starts a new
    chain segment (the old public key is retained for verification).

3. Authentication and authorization

  • Factors: password (as above); TOTP (RFC 6238, ±1 step, step-replay rejected, 10 single-use recovery
    codes); WebAuthn/passkeys planned for phase 2.
  • Sessions: 256-bit random bearer tokens. Only the SHA-256 hash is stored. 30-day absolute and
    14-day idle expiry. The token is rotated after MFA (no session fixation). A half-authenticated MFA
    session can only call /auth/mfa/verify, and wrapped keys are released only after all factors pass.
  • Brute force: per-IP and per-account token buckets (VNAS_AUTH_RATE_PER_MIN, default 10/min), plus
    exponential account lockout after 5 failures (capped at 1 h), plus alerting.
  • RBAC:
Global role Can
admin Everything a user can, plus manage users, roles, quotas, invites, groups and the audit log. Cannot decrypt anyone's data
user Create spaces, share, create links
readonly Read spaces shared with them; every write is refused server-side
guest Use only spaces shared with them; cannot create spaces, share, look up users, or create links
Space role Can
owner Manage members, rotate keys, delete the space
editor Create, update and trash items; upload; create links
viewer Read

Every handler resolves the caller's access to the target space first. Unknown and forbidden
both return 404, so IDs cannot be probed. Vault entries are excluded from public links.

4. Threat model and controls

T2 Compromised server or host / malicious admin Zero-knowledge E2EE; AAD binding; signed manifests; chunk ID ↔ plaintext verification; truncation checks; no admin reset; audit log signed + hash-chained Metadata visible (sizes, timing, sharing graph); availability (deletion); public-key substitution (§2.4); serving malicious web JavaScript — prefer desktop/mobile apps, which are signed and pinned

T10 Account takeover by brute force / credential stuffing Argon2id, rate limits, lockout, TOTP, alerts on failure bursts —

A leaked link can be revoked instantly, but not un-leaked

5. Transport and HTTP hardening (server/internal/httpx)

Content-Security-Policy: default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self'; img-src 'self' blob: data:; connect-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self',
plus Strict-Transport-Security, X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: no-referrer,
Permissions-Policy, Cross-Origin-Opener-Policy/-Resource-Policy: same-origin, and Cache-Control: no-store on the API.
Server timeouts (header 10 s, read/write 5 min, idle 2 min), header cap 32 KiB, body cap = chunk size + 64 KiB.

6. Logging and audit

Audited actions include: sign-in success and failure, MFA events, recovery, password change, device
enrol/revoke, item create/update/trash/purge/restore, direct vault-entry reads (GET /items/{id};
bulk sync of a vault is not logged per entry), file versions, shares,
key rotations, link create/open/revoke, and all admin actions. Rows carry actor, device, IP and
target IDs, never names or content (names are encrypted anyway).

Tamper resistance: SQLite triggers reject UPDATE/DELETE; each row stores SHA-256(prev_hash ‖ row)
and an Ed25519 signature. vnasd audit-verify checks the whole chain. For defense against a fully
compromised host, also forward rows to a separate append-only sink (for example a remote syslog or a
WORM S3 bucket); this is planned for phase 2.

7. Updates and patching

  • Semantic versioning. Security fixes ship as PATCH releases with a SECURITY changelog entry and a GitHub advisory.
  • Server: docker compose pull && docker compose up -d (or replace the binary). Migrations run automatically
    and are forward-only, so back up before upgrading. Roll back by restoring the pre-upgrade snapshot (§DEPLOYMENT 5).
  • Desktop: the Tauri updater downloads latest.json, verifies the minisign signature against the public key
    compiled into the app, and installs. Installers are additionally Authenticode / Apple-notarized when certificates are configured.
  • Mobile: store releases, and signed Expo OTA updates for JS-only fixes (codeSigningCertificate).
  • Web: the service worker is network-first, so a patched server delivers patched UI on the next load.
  • Dependencies: Dependabot weekly, nightly CI vulnerability scans, and CI fails on HIGH/CRITICAL.

8. Known limitations (by design or pending)

  • Structural metadata is visible to the server (see T2). Padding of chunk sizes is a possible future hardening step.
  • The web client trusts the server to serve honest JavaScript. Use desktop/mobile apps for maximum assurance.
  • WebAuthn, OPAQUE, key transparency and off-box audit shipping are pending (see ROADMAP).
  • Full-text search runs on clients only.
  • Intake links (T12): rotating a space key reissues a fresh keypair for every active intake link, so a removed member
    loses the ability to decrypt future submissions through it — but this is not retroactive for submissions received
    before rotation, and the total-size cap on a submission is enforced at commit time rather than streamed per chunk
    (bounded in the meantime by per-IP/per-link rate limits and the existing chunk GC, not by a hard per-byte gate).

9. Reporting vulnerabilities

Report privately through GitHub: open a private security advisory.
Only the maintainers can see it. Please don't open a public issue for security problems.
We aim to acknowledge reports within 72 h and ship fixes for critical issues within 14 days.
