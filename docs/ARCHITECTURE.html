Architecture

1. Principles

  1. Zero-knowledge server. Content, names, tags and keys are encrypted client-side. The server
    stores ciphertext and enforces who may fetch which ciphertext. It is a storage and
    coordination service, not a trusted party.
  2. One crypto implementation. All clients (web, desktop, mobile, AI agent) share
    @vnas/core (TypeScript + libsodium). One tested codebase, so the platforms cannot drift apart.
  3. Offline-first. Clients read from an encrypted local cache and write through an outbox.
    The network is an optimization.
  4. Boring, auditable server. Go standard library, chi router, SQLite, and three small
    dependencies. One static binary, no runtime.

3. Domain model

Concept Meaning
User An account with a global role: admin, user, readonly, guest
Device A client install. Enrolled at login, can be revoked, and may be flagged is_agent
Space A unit of encryption and sharing: a drive, vault, notebook (notes), or records collection. It has one symmetric space key per epoch
Member (space, user, role owner/editor/viewer, space keyring sealed to the user's public key)
Item A folder, file, note, secret (vault entry), or record. Each item has its own item key, wrapped by the space key
Version An immutable file revision: encrypted manifest plus ordered chunk list
Chunk Up to 4 MiB of file data, encrypted. Its ID is a keyed BLAKE2b hash of the plaintext
Change A row in the global, monotonic change feed that drives delta sync

Sharing a folder means making it its own space (or a sub-space) and adding members. Groups are
directory entries: sharing with a group seals the space key to each member individually.

4. Stack choices and why

Layer Choice Rationale
Server language Go Memory-safe, strongly typed, excellent stdlib crypto/TLS/HTTP, static cross-compiled binaries for all OSes and ARM boards (Raspberry Pi, Synology), and fast security patch releases. Rust would be equally safe but slower to iterate on
Database SQLite (default) A vNAS is usually one household or team on one box. SQLite needs no extra daemon, its backup is one file (VACUUM INTO), and WAL mode handles concurrent readers. SQL is kept portable. PostgreSQL is the planned option for multi-node or high-availability setups (roadmap phase 4)
Search Client-side The server cannot index ciphertext. Clients search their decrypted cache. Planned: SQLite FTS5 on desktop/mobile, an in-memory index on the web, and the agent's semantic index
Blob storage BlobStore interface Local disk today. NFS/SMB mounts work as local paths. S3-compatible (MinIO, Garage, B2) is the next backend
Client crypto libsodium Audited and misuse-resistant, with the same primitives on every platform (WASM on web/Node, native via react-native-libsodium on mobile)
Web React + Vite, PWA Ubiquitous; the PWA gives installable offline use. CSP: script-src 'self' 'wasm-unsafe-eval'
Desktop Tauri v2 ~10 MB installers (vs ~100 MB for Electron), Rust backend, OS keychain, minisign-verified auto-updates, least-privilege capability system
Mobile Expo / React Native Shares TypeScript with web and core. SecureStore uses the Keychain/Keystore, plus biometrics, SQLite, background fetch, and signed OTA updates
AI Ollama default; any OpenAI-compatible API Local-first. llama.cpp llama-server, LM Studio and vLLM also speak the OpenAI API. Cloud providers only behind an explicit policy
TLS Caddy Automatic Let's Encrypt/ZeroSSL, HTTP/3, modern defaults
Backups restic Encrypted, deduplicated, many backends, built-in integrity checks

5. Request flow examples

Upload (Vnas.prepareFile → SyncEngine):

  1. Generate an item key, split the file into 4 MiB chunks, compute id = BLAKE2b-256(key=itemKey, chunk), and encrypt each chunk.
  2. Build the manifest ({size, chunks:[{id,size}], signer}), sign it with Ed25519, then encrypt it.
  3. Queue create item + commit version in the outbox (this works offline).
  4. When online: POST /chunks/missing, then PUT only the missing chunks (resumable, parallel ×4), then POST /versions.

Download: fetch the version, decrypt the manifest and verify its signature, fetch and decrypt the chunks,
check each chunk's ID against its plaintext, then check total size (catches truncation, reordering and substitution).

Share: look up the recipient's public key, seal the space keyring to it, then PUT /spaces/{id}/members/{uid}.
Unshare: remove the member, generate a new epoch key, re-seal it to the remaining members, then POST /rotate.
