Sync and offline operation

Implementation: packages/core/src/sync.ts, server/internal/content/items.go. Covered by
packages/core/test/e2e.test.ts, which simulates two devices editing the same items offline.

Local state per device

Store Contents Web Desktop Mobile
meta sync cursor, key bundle (KDF params + wrapped keys), raw spaces IndexedDB IndexedDB (system webview) SQLite
items raw items, i.e. the same ciphertext the server holds IndexedDB IndexedDB SQLite
outbox queued, already-encrypted operations (including encrypted chunks) IndexedDB IndexedDB SQLite
unlock key AMK memory only memory, or OS keychain if "remember" memory, or Keychain/Keystore + biometrics

Because the cache is ciphertext, being offline does not reduce security. Offline unlock
re-derives the wrap key from the password, unwraps the cached wrappedAmk, and opens the cache. No
server is needed (Vnas.unlockOffline, tested in e2e).

Write path

  1. UI calls client.prepareCreate/Update/Delete/prepareFile. The op is encrypted immediately.
  2. engine.enqueue(op): apply optimistically to the local cache (revision = -1 marks "pending"), then
    persist to the outbox, then trigger a sync.
  3. flush(): send ops in order. baseRevision = -1 means "the revision my own earlier pending write
    produced" and is resolved from the results of earlier ops in the same flush.
  4. Network error, 5xx or 429: stop and keep order; retry on the next tick, the online event, or a background task.

Read path (delta sync)

pull(): GET /sync/changes?since=cursor pages through the latest change per item in every space
the user belongs to, upserts or removes cached items, and stores the new cursor. Items with pending
local ops are skipped until those ops flush (local intent wins until confirmed). Membership changes
(member/space ops) reload the space list: new spaces are snapshotted with ?all=1, and revoked
spaces are dropped from the cache.

Triggers: every 30 s (web/desktop), 60 s (agent), OS background fetch every ~15 min (mobile), window
online event, and after each local write. Planned for phase 2: a server-sent-events push channel.

Files: delta and resumable

  • 4 MiB chunks with content-derived IDs (keyed BLAKE2b). Editing the end of a large file
    re-uploads only the changed chunks; the others are found via POST /chunks/missing.
  • Chunk upload is idempotent, so an interrupted upload resumes by asking again which chunks are missing.
    Uncommitted chunks are garbage-collected after 24 h.
  • Versions are immutable. The last 50 are kept per file (VNAS_VERSIONS_TO_KEEP).

Conflict rules

Every write carries baseRevision. A mismatch yields 409 with the server's current item, and
Vnas.resolveConflict decides:

Situation Resolution Data loss?
Rename / move / tag edit (metadata only) Rebase onto the server state; last writer wins Previous name only
Vault entry edited on two devices Field-level merge: each field keeps the newer updatedAt (e.g. password from A, username from B) No
Note body edited on two devices Keep the server version; save the local version as "… (conflict YYYY-MM-DDTHH:MM)" No
File edited on two devices The local version becomes current; the other remains in version history No
Delete vs. edit Edit wins; the delete is dropped and the user notified No
Create replayed after a crash 409 exists treated as success No

The UI receives onConflict(itemId, note) and shows a toast. A conflict-review screen that diffs
two note versions side by side is planned for phase 2.

Trash and retention

Delete is a soft delete of the whole subtree (deleted_at). Restore brings back exactly what was
trashed together. Purge is permanent. Trash auto-purges after 30 days (VNAS_TRASH_RETENTION).
