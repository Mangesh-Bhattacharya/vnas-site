1. The core problem, and the design answer

With end-to-end encryption, the server cannot run an AI over your data. It only has ciphertext.
Whatever runs the model must hold keys. vNAS solves this without weakening the model:

The assistant is a separate vNAS account with its own keys. You share selected spaces with it
(viewer role) exactly as you would with a person. Consequences:

  • Least privilege: it can read only what you shared. Your vault is not shared by default, and even
    if you share it, the agent refuses to index secret items.
  • Instant revocation: unshare the space (and the key rotates), or revoke the agent's device.
  • No cross-user leakage by construction: one agent account per user. Retrieval is additionally
    filtered by space on every request.
  • It never holds your master key, so a compromised agent host exposes only the shared spaces.
 You ──share "Notes" (viewer)──► assistant@home account
                                      │ syncs + decrypts shared spaces only
                                 vnas-agent (Node) ──► Ollama / llama.cpp (local)
                                      │                 └─ or cloud API (opt-in, redacted)
 web / desktop / mobile ──Bearer token──► /v1/chat, /v1/summarize, /v1/suggestions, /v1/coach

2. Capabilities

Capability How
Natural-language search and Q&A Hybrid retrieval (embeddings via nomic-embed-text + lexical scoring) over notes, records and text files. Answers cite documents with their paths
Summarization /v1/summarize
Organization help /v1/suggestions: tags, folders and renames from metadata only
Security hygiene coaching Weak/reused/old passwords are detected on your device (core/hygiene.ts). Only the findings (no secrets) go to /v1/coach for plain-language advice
Sharing-risk alerts /v1/insights: over-broad shares. The admin audit log covers link creation and opens

3. Privacy controls

Control Default Setting
LLM location Local (Ollama) LLM_PROVIDER=ollama or openai + LLM_LOCALITY=local|cloud
Cloud allowed at all No: the agent refuses to start with a cloud LLM unless enabled AI_CLOUD_ALLOWED=true
Which spaces may go to the cloud none AI_CLOUD_SPACES=<space ids>
Redaction before cloud calls On: emails, phones, card numbers (Luhn), IBANs, API keys, JWTs, private keys, password: … patterns, IPs, SSNs → [EMAIL_1]… and restored locally in the answer AI_REDACT
Context size sent 12 000 characters AI_MAX_CONTEXT_CHARS
Vault secrets Never indexed, never sent not configurable
Prompt injection Document text is wrapped in <document> tags with a system rule to treat it as untrusted data; the assistant has no write or share tools, so injected instructions cannot act —

4. Choosing a model (all free)

Hardware Suggested model (via Ollama)
Raspberry Pi 5 / small NAS (8 GB) llama3.2:3b or qwen2.5:3b. Slow but works
Laptop / mini PC (16 GB) llama3.1:8b, qwen2.5:7b, mistral-nemo
GPU 12–24 GB qwen2.5:14b, gemma2:27b
Embeddings nomic-embed-text (274 MB)

ollama pull llama3.1:8b && ollama pull nomic-embed-text

5. Running it

# 1. In vNAS: create an account for the assistant (an invite with role "user"),
#    then from YOUR account share the spaces it should know about, as viewer.
# 2. Start it
VNAS_URL=https://nas.example.org AGENT_EMAIL=assistant@example.org \
AGENT_PASSWORD_FILE=/etc/vnas/agent-password LLM_PROVIDER=ollama \
node apps/agent/dist/main.js
# 3. Copy agent-state/client-token into the web/desktop app → Assistant → Connection

With Docker: docker compose --profile ai up -d (see DEPLOYMENT.md). On a laptop, desktop users can
run the agent locally next to Ollama for a fully offline assistant.

6. Extending

  • Providers: implement ChatProvider / Embedder (packages/ai/src/providers.ts).
  • Extractors: extractText in apps/agent/src/main.ts handles notes, records and text files. Add
    PDF (pdf.js), Office (mammoth) or OCR (tesseract.js) there.
  • Persistence: the index is rebuilt from the sync cache on start. For large libraries, persist
    vectors in an encrypted SQLite + sqlite-vec file keyed from the agent's keystore (roadmap).
